# Tool Safety 模块

面试考点: 工具调用安全、Schema校验、权限控制、审计追踪

## 核心实现

### SafeToolExecutor (`safe_tool_executor.py`)

**三层防护架构**:

```
┌─────────────────────────────────────────┐
│  第一层: SchemaValidator (参数硬校验)    │
│  - JSON Schema校验                      │
│  - 类型检查、范围限制、枚举值             │
│  - 负面描述（如"不要从地址解析城市名"）   │
└─────────────────────────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│  第二层: PermissionGuard (权限控制)      │
│  - 风险等级分类: LOW/MEDIUM/HIGH/CRITICAL │
│  - 最小权限原则                          │
│  - 高风险操作需人工确认                   │
└─────────────────────────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│  第三层: AuditLogger (审计追踪)          │
│  - 所有操作完整记录                      │
│  - 异常检测（高频调用告警）               │
│  - 支持一键重现                          │
└─────────────────────────────────────────┘
```

**运行**:
```bash
python tool_safety/safe_tool_executor.py
```

## 面试Q&A

**Q: 工具描述写得再好，模型也瞎传参数怎么办？**

A: 三层防护：
1. Schema里写清楚'负面描述'，明确说'城市名直接用用户输入，不要从地址解析'
2. 模型输出后用Pydantic硬校验，类型不对直接打回重试
3. 关键参数做业务兜底，比如order_id必须先调用'订单是否存在'校验接口

**Q: 如果Agent错误删除了数据，怎么防范？**

A: 三个核心原则：
1. **可审计**: 所有写操作支持dry-run模式，先返回预览再执行
2. **可回滚**: 操作分级，删除/支付等高风险操作需二次确认+通知第二责任人
3. **最小权限**: Agent操作账号最小权限，通过内部审批申请
